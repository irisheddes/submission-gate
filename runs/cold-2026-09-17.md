## How it was run

The auditor as a new user would get it: `reference/` held only `CONTEXT.md` and `LOADING.md`,
`package/` was empty, and the folder was staged outside any workspace with instruction files.
The applicant opened it without instructions and supplied the rulebook and the package when the
session asked for them. The session then ran `reference/LOADING.md` steps 1–5 itself (two
extractors reconciled, sections, provision map, requirement list) and audited.

**It loaded the 3 August 2026 edition of the Rules, not the July edition vendored in this
repository.** It checked the call page, found both, and used the later one (see
`../reference/SOURCES.md`, *A later edition exists*). So this run's requirement list and IDs are
its own and are not comparable row for row with `../reference/REQUIREMENTS.md`.

## What it found about this auditor

- **The vendored rulebook is not the latest edition, and the hash check cannot tell.** Recorded
  in `../README.md`, *What broke*.
- **`runs/CONTEXT.md` and `CLAUDE.md` disagree** about where a real run's full ledger goes: numbers
  only here, but "write the result to `runs/`" there. It kept the full ledger with the package,
  privately. Earlier sessions put it in a temporary folder. Open.
- **Loading a standard works without its author.** Steps 1–5 were followed from the page alone,
  and every citation resolved. Steps 6–8, fixtures, need a person, so its first audit came from
  an instrument untested on that edition, and the ledger said so.
- **Requirement lists differ between loads.** It derived 21 rows, giving post-selection
  obligations their own `NOT APPLICABLE` rows, where this repository scopes them out and lists 12.
  `LOADING.md` step 5 does not pin the scoping rule. Open.
